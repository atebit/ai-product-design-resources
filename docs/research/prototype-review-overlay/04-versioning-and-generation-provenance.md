# Versioning and Generation Provenance for Reviewed Prototypes (2026)

**Scope.** This document answers one question: how does a drop-in review overlay know *which version* of a prototype it is looking at and *what produced it* — which vibe-coding session, prompt, skill, model, and design-system version — so that a comment or grade lands on the right generation and the tuning loop receives the context it needs, across sessions. It covers stamping the page at generation time, what Claude Code (and Cursor, Codex, Copilot) can supply automatically, content-addressed version keys, the identifiers a tuning loop needs and how tracing systems carry them, which provenance standards are worth borrowing, comparing two generations in the browser, and cross-session continuity. Out of scope: how a comment is anchored to a DOM element and re-anchored after edits (the overlay stream's anchoring document), the review surfaces themselves ([design-sdlc/02](../design-sdlc/02-feedback-on-code-prototypes-and-flows.md)), and how grades are produced or fed back. It complements the grade record's `generator` block in [eval-tuning-loops/01 §4](../eval-tuning-loops/01-grading-generated-prototypes.md), the grade-storage and provenance section of [eval-tuning-loops/05 §2](../eval-tuning-loops/05-loop-architecture-and-governance.md), the prototype ledger row in [skill-resources/prototype-governance.md](../../../skill-resources/prototype-governance.md), and the lifecycle in [design-sdlc/03](../design-sdlc/03-prototype-governance-outside-the-codebase.md); none of that is repeated. Constraints carried throughout: the overlay must drop into single-file HTML with no build step (Claude Code artifacts, static mockups, construction-file builder output) *and* into Vite/React/Next dev apps, for a small shared team. Every vendor and tooling claim was checked against the live page on 2 September 2026; anything not fetched is marked "search-verified only" or "not verified."

## 1. Stamping the page at generation time

### What it is
Embedding provenance *in the artifact itself* — `<meta>` tags, a JSON `<script>` block, `data-*` attributes on `<html>`, a sidecar `build-info.json`, or build-time constant injection (Vite `define`, Next `NEXT_PUBLIC_*`) — so that anything that opens the page, including an overlay script, can read who and what made it without a database lookup.

### Why it matters
The overlay's constraint is that it must work in a file someone double-clicked. There is no server to ask, so the page has to carry its own identity. A stamp that survives copy-paste, hosting moves, and framework changes is the only thing that lets a comment left on `invite-sheet.html` on a laptop be reconciled with the same generation reviewed in a Claude Code artifact a week later.

### Key findings
- **The `generator` meta is the only standardized "who made this" slot, and it is a free-form string.** The HTML Standard says the value "must be a free-form string that identifies one of the software packages used to generate the document" and "must not be used on pages whose markup is not generated by software" ([WHATWG](https://html.spec.whatwg.org/multipage/semantics.html)). It is human-readable, one string, and unstructured — fine as a scanner-friendly marker ("this page is generated"), useless as a carrier for session IDs and hashes. The WHATWG MetaExtensions registry, where "you may add your own values to this list," already holds provenance-adjacent names — `revision` ("version from underlying control system"), `page-version`, `dc.created`, `dcterms.modified` — but nothing for model, prompt, or session ([WHATWG wiki](https://wiki.whatwg.org/wiki/MetaExtensions)). Use `generator` for the marker and put structure elsewhere.
- **A `<script type="application/json" id="…">` block is the right structured carrier for single-file HTML.** Browsers do not execute unknown script types, the block is reachable with `document.getElementById(id).textContent`, it survives any framework and any host, and it needs no build step. This is a design conclusion, not a vendor finding; the analogous precedent is the source-map rule that "consumers shall ignore any additional unrecognized properties … so that additional features can be added to this format without breaking existing users" (ECMA-426 draft, which also formalized the once-vendor-prefixed `x_google_ignoreList` as `ignoreList`) ([TC39](https://tc39.es/ecma426/)). The stamp schema in §10 adopts the same rule: unknown keys are ignored, and a `schema` field names the version.
- **Frameworks already stamp `<html>` — copy the pattern.** When Next.js has a `deploymentId` it "injects a `data-dpl-id` attribute on the `<html>` element," appends `?dpl=` to asset URLs, and sends `x-deployment-id` on navigations for skew detection; it can be set from `NEXT_DEPLOYMENT_ID` and, when set, `generateBuildId` "has no effect" ([Next.js deploymentId](https://nextjs.org/docs/app/api-reference/config/next-config-js/deploymentId); [generateBuildId](https://nextjs.org/docs/app/api-reference/config/next-config-js/generateBuildId)). A `data-proto-version` on `<html>` is the cheapest read for an overlay (`document.documentElement.dataset.protoVersion`) and the right place for the *version key*; the JSON block holds the rest.
- **Build-time injection for Vite and Next.** Vite's `define` entries "will be defined as globals during dev and statically replaced during build"; values must be JSON-serializable strings, with the docs' own example `__APP_VERSION__: JSON.stringify('v1.0.0')` ([Vite config](https://vite.dev/config/shared-options.html)). `import.meta.env` values are "statically replaced at build time," and only `VITE_`-prefixed variables reach the client ([Vite env](https://vite.dev/guide/env-and-mode.html)). Next inlines `NEXT_PUBLIC_*` "at build time, into the js bundle," so "all `NEXT_PUBLIC_` variables will be frozen with the value evaluated at build time" ([Next env](https://nextjs.org/docs/app/guides/environment-variables)) — which is exactly the property a provenance stamp wants. On Vercel, `VERCEL_DEPLOYMENT_ID` (`dpl_…`), `VERCEL_GIT_COMMIT_SHA`, `VERCEL_GIT_COMMIT_REF`, and `VERCEL_BRANCH_URL` are available at "both build and runtime" once "Enable access to System Environment Variables" is checked ([Vercel system env](https://vercel.com/docs/environment-variables/system-environment-variables)).
- **Git-revision plugins are a commodity; pick one that writes a meta tag.** Several small Vite plugins expose `GIT_COMMITHASH`-style globals ([@jinixx/vite-plugin-git-revision](https://www.npmjs.com/package/@jinixx/vite-plugin-git-revision), [vite-plugin-git-commit-hash](https://socket.dev/npm/package/vite-plugin-git-commit-hash); search-verified only). [vite-plugin-version-mark](https://github.com/ZhongxuYang/vite-plugin-version-mark) (91 stars) injects via "console output, global variables, meta tags, and static files" with `ifGitSHA`, `ifMeta`, `ifGlobal`, `ifExport`, and a `command` option for custom commands, and writes `<meta name="application-name" content="{APPNAME_VERSION}: {version}">` — a misuse of `application-name` per the HTML spec, but the only plugin that covers all four channels. For this overlay, a ten-line custom plugin that emits the §10 JSON block via `transformIndexHtml` is better than any of them.
- **The vendors stamp attribution, not provenance.** Lovable's generated `index.html` carries `<meta name="author" content="Lovable" />`, `<meta name="description" content="Lovable Generated Project" />`, and a `lovable.dev` OG image (verified on a [published Lovable project](https://huggingface.co/spaces/jurmy24/leLab/blob/main/index.html)). v0 adds a visible "Built with v0" badge on deployed sites ([Vercel community](https://community.vercel.com/t/request-to-remove-built-with-v0-watermark/15306), search-verified only). Figma Make packages an `Attributions.md` listing assets that require attribution (search-verified only). Bolt: nothing found. **None records a version, prompt, model, or design-system revision in the output** — the same gap [design-sdlc/03](../design-sdlc/03-prototype-governance-outside-the-codebase.md) found for DS versions. The overlay must add the stamp itself, and the `author` meta is a weak "this came from Lovable" signal at best.

| Carrier | Readable by overlay via | Survives copy to another host | Needs build step | Best for |
|---|---|---|---|---|
| `<meta name="generator">` | `querySelector('meta[name=generator]')` | Yes | No | Human/scanner marker only |
| `<html data-proto-version="…">` | `documentElement.dataset` | Yes | No | The version key (one string) |
| `<script type="application/json" id="proto-provenance">` | `getElementById().textContent` → `JSON.parse` | Yes | No | The full stamp |
| `/build-info.json` sidecar | `fetch()` | No (separate file) | No | Multi-page dev apps; not for single-file artifacts (CSP blocks fetch to anything but own origin in Claude Code artifacts, and relative links "do not resolve" there) |
| Vite `define` / `import.meta.env` | Global constant | Yes (inlined) | Yes | Vite/React dev apps |
| Next `NEXT_PUBLIC_*`, `deploymentId` | Inlined constant, `data-dpl-id` | Yes | Yes | Next apps on Vercel |
| Source-map `x_*` field | Source-map consumer only | Bundled apps only | Yes | Not worth it for review; noted for completeness |

### Open questions
- Should the stamp be inside the file (survives moves, changes the file hash) or beside it (does not change the hash, does not survive moves)? §3 resolves this by excluding the stamp from the hash.
- No vendor exposes a "generated with prompt X in session Y" field; will the C2PA-style pressure on media (§5) reach app builders?

## 2. What Claude Code (and its peers) can supply

### What it is
The identifiers Claude Code exposes automatically — to hooks, the status line, `-p` JSON output, and OpenTelemetry — that a stamp can capture without anyone typing them, and where the boundaries are (no turn index, no skill version field, model not always present).

### Why it matters
Every field the tooling captures for free is one the team never forgets to declare. The difference between "which session produced this" being a lookup and being a memory exercise is whether a hook wrote `session_id` into the file at generation time.

### Key findings
- **Every hook receives `session_id`, `transcript_path`, `cwd`, `hook_event_name`, `permission_mode`, and (v2.1.196+) `prompt_id`** — "UUID identifying the user prompt currently being processed. Matches OpenTelemetry `prompt.id` attribute" — plus `agent_id` and `agent_type` when the hook "fires inside subagent" ([hooks reference](https://code.claude.com/docs/en/hooks)). `transcript_path` "is written asynchronously and may lag the in-memory conversation," so a stamping hook should read the JSON it is given, not the transcript. The environment also exposes `CLAUDE_PROJECT_DIR`; `OTEL_*` exporter variables "are removed" from the hook process.
- **`SessionStart` is the one place the model appears — sometimes.** Its input carries `source` (`startup`, `resume`, `clear`, `compact`, `fork`) and, on resume, `seconds_since_last_response` and `context_tokens`; the docs' example includes `"model": "claude-opus-5"` but state that "only `SessionStart` hooks can receive a `model` field, and Claude Code doesn't always include it." `SessionStart` can return `hookSpecificOutput.additionalContext` ("added to Claude's context at the start of the conversation"), `initialUserMessage`, `watchPaths`, `sessionTitle`, and `reloadSkills`, and can persist environment variables by appending `export` lines to `$CLAUDE_ENV_FILE` (available to `SessionStart`, `Setup`, `CwdChanged`, `FileChanged` only). Output strings are "capped at 10,000 characters" ([hooks reference](https://code.claude.com/docs/en/hooks)).
- **`PostToolUse` on `Write|Edit` is the stamping point.** Its input includes `tool_name`, `tool_input` (`file_path` "always absolute," `content`), `tool_response`, `tool_use_id`, and `duration_ms` — so a hook can see that an `.html` file was just written and rewrite it with a stamp that records the `tool_use_id` and `prompt_id` of the turn that produced it. Caveat: "Claude Code doesn't run a `PostToolUse` hook matching `Edit|Write` when a `Bash` command … rewrites the same file"; use `FileChanged` for builder output produced by a shell command. Second caveat: a hook's rewrite is not a Claude edit, so `/rewind` will not restore the stamp ("checkpointing does not track files modified by bash commands"; [checkpointing](https://code.claude.com/docs/en/checkpointing)).
- **`Stop` and `SubagentStop` carry `last_assistant_message`, `stop_hook_active`, and (for subagents) `agent_transcript_path`**; `SessionEnd` carries `reason` (`clear`, `resume`, `logout`, `prompt_input_exit`, `other`) and has a 1.5-second default timeout, so a `SessionEnd` archiver must be fast or set a per-hook `timeout` ([hooks reference](https://code.claude.com/docs/en/hooks)).
- **Session IDs are UUIDs you can set, fork, name, and resume.** `--session-id` "must be a valid UUID"; `--fork-session` creates "a new session ID instead of reusing the original"; `--name`/`/rename` give a resumable display name; `claude -p --output-format json` returns "structured JSON with result, session ID, and metadata," and the docs' own recipe is `session_id=$(claude -p "…" --output-format json | jq -r '.session_id')` followed by `--resume "$session_id"` ([CLI reference](https://code.claude.com/docs/en/cli-reference); [headless](https://code.claude.com/docs/en/headless)). Transcripts live at `~/.claude/projects/<project>/<session-id>.jsonl`, but "the entry format is internal to Claude Code and changes between versions" ([sessions](https://code.claude.com/docs/en/sessions)) — do not parse them for provenance; use hook input and `-p` JSON. Subagent transcripts are at `~/.claude/projects/{project}/{sessionId}/subagents/agent-{agentId}.jsonl` ([subagents](https://code.claude.com/docs/en/sub-agents)). No documented hook field names a *parent* session after `--fork-session`; the stamp must carry `derived_from` by hand (not verified as available anywhere).
- **Skills have no `version` field; use `metadata`.** Claude Code's SKILL.md frontmatter reference lists `name`, `description`, `when_to_use`, `argument-hint`, `arguments`, `disable-model-invocation`, `user-invocable`, `allowed-tools`, `disallowed-tools`, `model`, `effort`, `context`, `agent`, `background`, `hooks`, `paths`, `shell`, `metadata` ("free-form YAML map for your own key-value data … Claude Code doesn't act on its contents"), `license`, and `compatibility` — no `version` ([skills](https://code.claude.com/docs/en/skills)). The Agent Skills spec's own example puts it in `metadata: { author: example-org, version: "1.0" }` ([agentskills.io](https://agentskills.io/specification)). Skills can substitute `${CLAUDE_SESSION_ID}` ("useful for logging, creating session-specific files, or correlating skill output with sessions") and `${CLAUDE_SKILL_DIR}` into their body, which is enough for a generation skill to write its own identity into a declared-fields file (§10). Skill invocations are also observable: the `UserPromptExpansion` hook fires "when a user-typed command expands into a prompt," and OTel's `tool_decision` event includes "skill names, subagent types" when `OTEL_LOG_TOOL_DETAILS=1`.
- **The status line receives the fullest snapshot.** Its stdin JSON includes `session_id`, `session_name`, `transcript_path`, `model.id`, `model.display_name`, `version` (Claude Code), `workspace.project_dir`, `workspace.git_worktree`, `workspace.repo.{host,owner,name}`, and `cost.total_cost_usd` ([statusline](https://code.claude.com/docs/en/statusline)). It is a display hook, not a lifecycle one, but it is the only documented place `model.id` is guaranteed — a status-line script that also writes `.proto/session.json` is a legitimate trick.
- **Artifacts and Claude Design.** Each artifact publish "becomes a version," the share menu shows "Sharing version N" with an "Always share latest version" toggle, and the Compliance API addresses `/artifacts/{artifact_id}/versions/{version_id}`, so versions have server-side IDs ([artifacts](https://code.claude.com/docs/en/artifacts)); the artifact URL (`claude.ai/code/artifact/<uuid>`) is the stable identity. Claude Design's help center documents "Handoff to Claude Code" with "Send to local coding agent" / "Send to Claude Code Web" and says "Use `/design-sync` to pull in your design system," but **does not enumerate the bundle's contents** ([Claude Design help](https://support.claude.com/en/articles/14604416-get-started-with-claude-design)); third-party writeups describe it as design files plus the producing chat plus a README ([Flowpoint](https://flowpoint.ai/blog/claude-design-to-claude-code), 17 Aug 2026) or component spec, tokens, layout hierarchy, and assets (search-verified only). No official page names a design-system revision identifier in the bundle; treat `ds_version` as declared.
- **Cursor, Codex, Copilot in one paragraph.** Cursor hooks receive `conversation_id` ("stable ID across multiple turns"), `generation_id` ("changes with each user message"), `model`, `cursor_version`, `workspace_roots`, and `transcript_path`, with `sessionStart`, `postToolUse`, `afterFileEdit`, `stop`, and `subagentStart/Stop` events configured in `.cursor/hooks.json` ([Cursor hooks](https://cursor.com/docs/hooks)) — `generation_id` is the turn identifier Claude Code's `prompt_id` gives you. Codex hooks (experimental) carry `session_id`, `cwd`, `hook_event_name`, `model`, and `turn_id` for turn-scoped events, in `~/.codex/hooks.json` or `<repo>/.codex/hooks.json` ([Codex hooks](https://learn.chatgpt.com/docs/hooks)). Copilot's `sessionStart` payload is `sessionId`, `timestamp`, `cwd`, `source` (`startup | resume | new`), optional `initialPrompt`; `postToolUse` gives `toolName`, `toolArgs`, `toolResult`; there is no model field; config lives in `.github/hooks/*.json` ([Copilot hooks reference](https://docs.github.com/en/copilot/reference/hooks-reference)). Across all four, the common automatic set is *session id + working directory + tool call*; model and turn id are present in three of four; skill/prompt version in none.

### Open questions
- `model` on `SessionStart` is optional and there is no documented `PostToolUse` model field; does the API-request `model` in OTel (`claude_code.api_request`) get joined to a `tool_use_id` reliably enough to backfill it? Untested.
- After `--fork-session` or `/branch`, is the original session ID recoverable from any hook input? Not documented.

## 3. Content-addressed versioning

### What it is
Using a digest of the artifact's bytes as the version key for comments and grades, so an unchanged page keeps its comments, a regenerated page gets a fresh key, and the key can be recomputed by anyone holding the file — plus how Vercel, Claude Code artifacts, Figma Make, Lovable, v0, and Bolt key their versions.

### Why it matters
A comment keyed to a URL or a filename silently migrates onto the next generation; a comment keyed to a deployment ID dies with the deployment. A content hash is the only key that is both stable (same bytes → same key on any machine) and honest (any change → new key), and it is computable in the browser without a server.

### Key findings
- **SHA-256 in the browser is one call, and it works in a double-clicked file.** `crypto.subtle.digest("SHA-256", new TextEncoder().encode(text))` returns an `ArrayBuffer`; MDN's example hex-encodes it with `Uint8Array.prototype.toHex` when available ([MDN digest](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/digest)). `SubtleCrypto` is secure-context only, but MDN states that `http://localhost`, `http://127.0.0.1`, and `http://*.localhost` "can be considered to have been delivered securely" and "the same is generally true for `file://` URLs" ([MDN secure contexts](https://developer.mozilla.org/en-US/docs/Web/Security/Secure_Contexts)) — so the overlay can hash in Vite dev, in a static file, and in an artifact.
- **Hash the bytes at write time, not the DOM at read time.** `document.documentElement.outerHTML` is a re-serialization: attribute order, entity encoding, and framework hydration change it, so two browsers can disagree. The reliable key is the SHA-256 of the file bytes *with the stamp block and the overlay `<script>` masked out*, computed by the hook or build plugin that writes the stamp (§10) and stored in `data-proto-version`. The overlay's in-browser hash is a fallback for unstamped pages and is labeled `unstamped:` so nobody mistakes it for a stable key.
- **Git blob SHAs are a second, free key when the file is in a repo.** Git hashes `"blob <size>\0" + content` and `git hash-object --stdin` reproduces it ([Pro Git](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)). It identifies the exact committed bytes, which makes it the right join key to the grade record's `artifact.commit`, but it changes whenever the stamp changes, so it cannot be the comment key unless the stamp is a sidecar. Record both: `content_sha256` (stamp-masked) as the comment key, `git_blob` as the repo join.
- **Subresource Integrity is the same idea with a different job.** `integrity="sha384-<base64>"` on `<script>`/`<link>` makes the browser refuse a mismatched resource ([MDN SRI](https://developer.mozilla.org/en-US/docs/Web/Security/Subresource_Integrity)). It is useful for pinning the overlay bundle loaded from a CDN inside an artifact (cdnjs and jsDelivr are on the artifact allowlist), not for versioning the page.
- **Vercel keys comments to project and branch, not to a single deployment.** Comments are "enabled by default on all preview deployments"; when "a new preview deployment has been generated, a popup modal … will prompt you to refresh your view"; the inbox is filtered "by selecting the branch name at the top"; and the localhost injection script takes `data-owner-id`, `data-project-id`, and `data-branch` ([Vercel comments](https://vercel.com/docs/comments); [using comments](https://vercel.com/docs/comments/using-comments); [localhost toolbar](https://vercel.com/docs/vercel-toolbar/in-production-and-localhost/add-to-localhost)). Inference from those three facts: a thread survives a redeploy of the same branch. An explicit sentence to that effect was not found on any fetched page — mark as inferred. The deployment itself is identified by `VERCEL_DEPLOYMENT_ID` and, in Next, `data-dpl-id`.
- **Claude Code artifacts version on every publish and let the owner pin what viewers see.** "Each publish becomes a version, and from the Share control … you can choose which version viewers see"; editors "publish new versions" by attaching the artifact; comments attach to the artifact, and threads can be activated for Claude ([artifacts](https://code.claude.com/docs/en/artifacts)). A stamp inside the artifact HTML is the only way to know *which* version a viewer commented on from inside the page, because the viewer's version choice is not exposed to the page's script (not documented; assume unavailable).
- **Figma Make keeps two buckets and freezes the old ones.** "The comment sidebar organizes comments into two sections — Current version and Other versions"; "you can only comment on the latest version"; each comment gets "a screenshot of the element's current state" ([Figma help](https://help.figma.com/hc/en-us/articles/38701587731735-Add-comments-in-Figma-Make)). That is the cleanest published version-vs-comment policy and the model for the overlay: comments belong to a version key; old-version comments are visible but read-only; the screenshot is the evidence that survives.
- **Lovable / v0 / Bolt: linear histories, restore semantics differ.** Lovable: "Every change Lovable makes to your project creates a version automatically"; bookmarks mark known-good versions; revert "restores your project's code only … It does not restore or roll back your database data" ([Lovable history](https://docs.lovable.dev/features/projects/history)). v0: "Each time v0 updates a code block from a message, it creates a new version"; "Restoring an old version creates a new, most recent version using the restored code to maintain a linear version history" ([v0 versions](https://v0.app/docs/versions)) — i.e., restore is a *new generation with identical bytes*, which is exactly what a content hash handles correctly (same key, comments carry). Bolt: "Version history … is a timeline of changes"; versions can be renamed and bookmarked; Export → Download yields a zip ([Bolt help](https://support.bolt.new/building/using-bolt/rollback-backup)). None exposes a stable version identifier the overlay can read from the page.

| System | Version identity | Comment scope | Redeploy / restore behaviour |
|---|---|---|---|
| Content hash (proposed) | SHA-256 of stamp-masked bytes | The hash | Identical bytes → same key, comments carry; any change → new key |
| Vercel | `dpl_…` deployment ID; `data-dpl-id` in Next | Project + branch (inferred) | New deployment prompts refresh; threads persist per branch (inferred) |
| Claude Code artifacts | Per-publish version, server IDs | The artifact | Owner picks the version viewers see |
| Figma Make | Per-generation version | Latest version only | Older-version comments filed under "Other versions," read-only |
| Lovable | Every change is a version; bookmarks | Element-pinned (see design-sdlc/02) | Revert restores code, not data |
| v0 | Per-message version | None native | Restore = new latest version, linear history |
| Bolt | Version history with labels/bookmarks | None native | Export zip; restore semantics not documented |

### Open questions
- Should whitespace-only or comment-only changes produce a new key? Masking the stamp is easy; canonicalizing HTML is not. Recommendation: no canonicalization; a new key with 100% re-anchored comments (§6) is cheap.
- Vercel's exact cross-deployment persistence rule needs a primary-source sentence; the CLI (`vercel comments --json`) output may reveal whether threads carry a deployment or branch field.

## 4. Session-level context capture for tuning

### What it is
The set of identifiers the tuning loop needs in every grade — the repo's `generator` block: `skill@version`, `rules_sha`, `exemplar_set`, `catalog_version`, `schema_version`, `model`, `prompt_sha`, `seed`, `temperature` — sorted into "captured automatically" and "must be declared," and how OpenTelemetry GenAI conventions, Langfuse/LangSmith, and Claude Code's OTel export can carry the same identifiers so a page can be linked to the turn that produced it.

### Why it matters
[eval-tuning-loops/01 §4](../eval-tuning-loops/01-grading-generated-prototypes.md) requires that "every grade names the task id, the skill/rules/exemplar-set version, the construction-file schema and catalog version, the model and prompt hash, and the seed/temperature — so doc 03 can attribute a regression to a rule edit." A grade whose generator block is blank is a data point the loop cannot use; the overlay is where those fields are cheapest to attach, because it is looking at the stamped page.

### Key findings
- **What is automatic and what is not.** From §2: `session_id`, `prompt_id`, `tool_use_id`, `cwd`, `agent_id`, Claude Code `version`, and (usually) `model` are automatic in Claude Code; `seed` and `temperature` are not exposed to hooks at all (Claude Code does not surface sampling parameters; not documented anywhere fetched) and are only meaningful in API pipelines; `skill@version`, `rules_sha`, `exemplar_set`, `catalog_version`, and `schema_version` are *declared by the generation skill* — but "declared" can still be mechanical: the skill's body computes `git hash-object .claude/rules/*.md` and reads its own `metadata.version`, then writes `.proto/generator.json`, and the hook merges it into the stamp. `prompt_sha` is the SHA-256 of the rendered prompt for API pipelines; in Claude Code the honest substitute is `prompt_id` plus the skill identity.
- **OpenTelemetry GenAI conventions already name most of the fields.** The registry (Development stability) defines `gen_ai.conversation.id` ("the unique identifier for a conversation (session, thread)"), `gen_ai.agent.id`/`gen_ai.agent.name`/`gen_ai.agent.version` ("the version of the GenAI agent"), `gen_ai.tool.call.id`, `gen_ai.request.model`, `gen_ai.response.model`, `gen_ai.request.temperature`, `gen_ai.request.seed` ("requests with same seed value more likely to return same result"), `gen_ai.response.id`, `gen_ai.prompt.name` and `gen_ai.prompt.version` ("the version of the prompt template used"), and `gen_ai.usage.*` ([semconv registry](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/registry/attributes/gen-ai.md); [spans](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md)). The mapping to the grade record is direct: `model` ↔ `gen_ai.response.model`, `seed`/`temperature` ↔ `gen_ai.request.*`, `skill@version` ↔ `gen_ai.agent.name`/`gen_ai.agent.version`, `prompt_sha` ↔ `gen_ai.prompt.name`+`version`. Use these names in the stamp so API-pipeline traces and Claude Code sessions land in one schema.
- **Claude Code's OTel export carries the join keys.** Events share `session.id`; every event from one prompt shares `prompt.id`; `claude_code.tool_result` has `tool_use_id` "matching hook data"; `claude_code.api_request` has `model`, `request_id`, and `client_request_id`; `claude_code.user_prompt` has `message.uuid`; `app.version` is available; and `OTEL_RESOURCE_ATTRIBUTES="department=…,team.id=…"` attaches custom keys to every event ([monitoring](https://code.claude.com/docs/en/monitoring-usage)). That last one is the cleanest way to put *declared* identifiers (`skill.version=proto-builder-1.4.2`, `ds.version=ds-core-7.2.0`) onto the trace without touching the stamp — set them in the shell that launches the session. `OTEL_TRACES_EXPORTER` is marked beta.
- **Langfuse and LangSmith have the same three slots.** Langfuse groups by `sessionId` ("all observations with the same `sessionId` will be grouped together"), carries `release` ("commonly … the semantic version or git commit hash," auto-read from `LANGFUSE_RELEASE` or Vercel/Netlify/Heroku env), `version` on any observation, and filterable metadata with values "limited to max 200 characters" ([sessions](https://langfuse.com/docs/observability/features/sessions); [releases](https://langfuse.com/docs/observability/features/releases-and-versioning); [metadata](https://langfuse.com/docs/observability/features/metadata)). LangSmith groups runs into threads via the reserved metadata keys `session_id` or `thread_id`, and attaches tags and metadata via `@traceable` or `langsmith_extra` ([threads](https://docs.langchain.com/langsmith/threads); [metadata](https://docs.langchain.com/langsmith/add-metadata-tags)). For an API pipeline, put `content_sha256` of the produced page in trace metadata; the overlay then links a comment to a trace by hash, not by time.
- **Linking a page to the turn.** The unit that produced a page is a *tool call* (`Write`/`Edit`), not a turn; a turn may write several files. The join is therefore `session_id` → `prompt_id` (the turn) → `tool_use_id` (the write), all present in `PostToolUse` input, all present in OTel. There is no "turn index" field; `prompt_id` is the turn's identity. For Cursor the equivalents are `conversation_id` → `generation_id`; for Codex `session_id` → `turn_id`. Record all three in the stamp's `generator` block under OTel-style names (`gen_ai.conversation.id`, `prompt.id`, `gen_ai.tool.call.id`) so the loop can join without a translation table.

| Grade-record field | Captured automatically by | Declared by | Notes |
|---|---|---|---|
| `model` | `SessionStart` hook (`model`, not always), statusline `model.id`, OTel `api_request.model` | Fallback: skill | Prefer statusline/OTel |
| `session_id`, `prompt_id`, `tool_use_id` | Every hook (`prompt_id` v2.1.196+) | — | Join keys to transcript and OTel |
| `skill@version` | `UserPromptExpansion` hook (name only), OTel `tool_decision` with `OTEL_LOG_TOOL_DETAILS` | Skill writes `metadata.version` to `.proto/generator.json` | No `version` frontmatter field exists |
| `rules_sha` | — | Skill runs `git hash-object` over `.claude/rules/*.md` and CLAUDE.md | Cheap, deterministic |
| `exemplar_set`, `catalog_version`, `schema_version` | — | Skill / construction-file builder | Ledger `ds_version` is the same value |
| `prompt_sha` | API pipeline only | — | In Claude Code, `prompt_id` substitutes |
| `seed`, `temperature` | API pipeline only (`gen_ai.request.*`) | — | Not exposed by Claude Code |
| `content_sha256`, `git_blob` | `PostToolUse` hook / build plugin | — | The version key (§3) |

### Open questions
- Can `OTEL_LOG_TOOL_DETAILS` output be joined to `tool_use_id` reliably enough to recover the skill name for a given write? Plausible from the docs; not tested.
- Should the overlay refuse to accept a grade when the stamp lacks `skill`/`catalog_version` (hard gate), or accept and mark the grade `provenance_incomplete`? The loop doc's "gates then scores" logic argues for the mark, not the refusal.

## 5. Provenance standards worth borrowing

### What it is
The existing standards for saying "this thing was made by that process from those inputs" — W3C PROV, C2PA, SLSA/in-toto, SPDX/CycloneDX AI-BOM, git trailers — assessed for what the overlay should borrow (vocabulary, envelope shape) versus what is overkill (signing, RDF, media bindings).

### Why it matters
Inventing a provenance schema from scratch guarantees it will not join with anything else. Borrowing the *shape* of a standard (subject digest + predicate) and the *names* of another (generated-by, derived-from, revision-of) costs nothing and keeps the door open to real attestations later.

### Key findings
- **PROV-O is the right vocabulary and the wrong serialization.** A 2013 W3C Recommendation with three starting classes — Entity ("a physical, digital, conceptual, or other kind of thing with some fixed aspects"), Activity ("something that occurs over a period of time and acts upon or with entities"), Agent ("something that bears some form of responsibility") — and the relations the stamp needs: `wasGeneratedBy`, `wasAttributedTo`, `wasDerivedFrom` ("a transformation of an entity into another, an update of an entity resulting in a new one"), `wasRevisionOf` ("the derived Entity contains substantial content from the original Entity"), `used`, `wasAssociatedWith` ([PROV-O](https://www.w3.org/TR/prov-o/)). PROV-JSON (a 2013 Member Submission) keys each relation by identifier for lookup ([PROV-JSON](https://www.w3.org/submissions/prov-json/)). Verdict: use the relation names as JSON keys (`wasGeneratedBy` = the session/turn/tool-call, `used` = skill, rules, exemplars, catalog, `wasRevisionOf` = previous content hash); skip the RDF and the qualified-influence pattern.
- **in-toto's Statement is the right envelope; SLSA's predicate is the right checklist; signing is optional.** A Statement is `{"_type": "https://in-toto.io/Statement/v1", "subject": [{"name", "digest": {"sha256": "…"}}], "predicateType": "<URI>", "predicate": {}}` and "subject artifacts are matched purely by digest, regardless of content type" ([in-toto](https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md)) — precisely the content-addressed key from §3. SLSA's `https://slsa.dev/provenance/v1` predicate separates `buildDefinition` (`buildType`, `externalParameters`, `internalParameters`, `resolvedDependencies`) from `runDetails` (`builder.id`, `metadata.invocationId`, `startedOn`, `finishedOn`) ([SLSA](https://slsa.dev/spec/v1.0/provenance)); mapped to generation, `externalParameters` = the prompt and declared fields, `resolvedDependencies` = skill, rules, exemplar set, catalog with digests, `invocationId` = `prompt_id`. GitHub's artifact attestations show the production path — `attest-build-provenance` produces "SLSA v1.0 Build Level 2" via Sigstore, verified with `gh attestation verify` ([GitHub](https://docs.github.com/en/actions/concepts/security/artifact-attestations)) — which is what to reach for if a *promoted* prototype ever needs a verifiable chain. For a small team's review overlay, an unsigned Statement-shaped JSON block is enough; "artifact attestations are *not* a guarantee that an artifact is secure" applies to provenance too.
- **C2PA does not cover HTML or code, and Anthropic's own credentials stop at images.** C2PA 2.2 (May 2025) binds manifests to media with `c2pa.hash.data` byte-range hashes and added `digitalSourceType` URIs for AI-generated content, but its asset model is media (images, video, audio, documents) and it "does not explicitly address generic text, HTML, or source code" ([C2PA 2.2](https://spec.c2pa.org/specifications/specifications/2.2/specs/C2PA_Specification.html)); IPTC's vocabulary supplies `trainedAlgorithmicMedia` ("created algorithmically using an Artificial Intelligence model trained on captured content") and `compositeWithTrainedAlgorithmicMedia` ([IPTC](https://cv.iptc.org/newscodes/digitalsourcetype/)). The 2026 movement is real but media-shaped: Anthropic now "weaves an imperceptible watermark directly into the text" for models launched on or after 2 August 2026 and attaches signed C2PA metadata to ".svg, .png, or .jpg" files, verifiable at claude.com/check-content; the help page "doesn't specifically address whether code is watermarked" ([Anthropic help](https://support.claude.com/en/articles/16266773-how-claude-marks-ai-generated-content)). The EU AI Office's Code of Practice on transparency of AI-generated content (June 2026) and OpenAI's provenance page were located by search only. Verdict: reuse the IPTC `digitalSourceType` string as a stamp field for *screenshots* the overlay captures; do not try to C2PA-sign HTML.
- **AI-BOMs describe models, not generated UI.** CycloneDX 1.5 (June 2023) added the `machine-learning-model` component type and `modelCard` ([CycloneDX](https://cyclonedx.org/capabilities/mlbom/); version detail search-verified only); SPDX 3.0.1's AI profile defines `AIPackage` with `typeOfModel`, `hyperparameter`, `safetyRiskAssessment`, energy fields, for "software packages, models, and datasets" ([SPDX](https://spdx.github.io/spdx-spec/v3.0.1/model/AI/AI/)). Both answer "what models are in this product," not "which model wrote this page." Overkill for the overlay; relevant only if the promoted product has to ship an AI-BOM, in which case the stamp's `model` field is the input.
- **`Assisted-by:` is the emerging commit-level convention; adopt it.** The Linux kernel's coding-assistants document (Linux 7.0, April 2026) specifies `Assisted-by: AGENT_NAME:MODEL_VERSION [TOOL1] [TOOL2]`, e.g. `Assisted-by: Claude:claude-3-opus coccinelle sparse`, and states "AI agents MUST NOT add Signed-off-by tags. Only humans can legally certify the Developer Certificate of Origin" ([kernel docs](https://docs.kernel.org/process/coding-assistants.html); format example via [It's FOSS](https://itsfoss.com/news/linux-ai-coding-assistants-policy/)). A Claude Code plugin already enforces it with a `PreToolUse` hook on `git commit` ([bcmyguest/assisted-by](https://github.com/bcmyguest/assisted-by); note its restrictive "all rights reserved" license). GitHub's `Co-authored-by: name <email>` trailer, blank-line separated ([GitHub docs](https://docs.github.com/en/pull-requests/committing-changes-to-your-project/creating-and-editing-commits/creating-a-commit-with-multiple-authors)), is what Claude Code emits by default; git's `interpret-trailers` makes either machine-readable ("trailer lines that look similar to RFC 822 e-mail headers, at the end of the … commit message") ([git](https://git-scm.com/docs/git-interpret-trailers)). Verdict: keep `Co-Authored-By` for attribution, add `Assisted-by: Claude:<model-id>` for the model, and add a `Prototype: PROTO-YYYY-NNN` trailer that the ledger-link gate in [skill-resources/prototype-governance.md](../../../skill-resources/prototype-governance.md) already checks for.
- **`.ai-provenance` is not a standard.** Searches for a repository-level AI-provenance file convention returned an AIBOM schema paper extending CycloneDX, a GitHub topic tag, and policy documents — no adopted file format ([GitHub topic](https://github.com/topics/ai-provenance); search-verified only). Do not wait for one; the sidecar layout in §10 is the repo-level file.

| Standard | Borrow | Skip | Verdict |
|---|---|---|---|
| PROV-O / PROV-JSON | Relation names (`wasGeneratedBy`, `used`, `wasRevisionOf`) | RDF, qualified pattern | Vocabulary only |
| in-toto Statement | `subject[].digest` + `predicateType` envelope | DSSE signing (until promotion) | Adopt shape |
| SLSA provenance v1 | `externalParameters` / `resolvedDependencies` / `invocationId` split | Build levels, builder trust | Checklist for the predicate |
| GitHub artifact attestations | For promoted prototypes in CI | For review-time stamps | Later |
| C2PA + IPTC digitalSourceType | `trainedAlgorithmicMedia` string on captured screenshots | Manifests on HTML | Not applicable to code |
| CycloneDX ML-BOM / SPDX AI | `model` field as future AI-BOM input | Everything else | Overkill |
| `Assisted-by:` / `Co-Authored-By` trailers | Both, plus `Prototype:` trailer | — | Adopt |
| `.ai-provenance` file | — | — | No standard exists |

### Open questions
- Will Anthropic's text watermark survive in generated HTML/JS, and if so does it constitute provenance the overlay could read? The help page is silent on code; nothing to build on yet.
- At what point does a small team want signed attestations — when a prototype is promoted to a PR, or never?

## 6. Comparing versions in the overlay

### What it is
Showing a reviewer what changed between two generations of the same prototype — DOM diff, pixel diff, side-by-side — inside the browser with no build step, and deciding which comments from the old version still apply.

### Why it matters
A reviewer returning to a regenerated page has two questions: "what changed?" and "did my last comments get addressed?" Figma Make answers the second with a version filter; GitHub answers the first for code with "changes since your last review." The overlay has to do both from two HTML files and a list of anchored comments.

### Key findings
- **Side-by-side iframes cost nothing.** Two `<iframe srcdoc="…">` elements with synchronized scroll and a shared viewport width need no library and respect each version's own CSS; this is the baseline for every comparison and the only mode that works when the two versions use different frameworks. (Design conclusion; no vendor source.)
- **DOM diff: diffDOM works in the browser but is LGPL.** It abstracts "differences between DOM elements as a 'diff' object, representing the sequence of modifications that must be applied to one element in order to turn it into the other," loads via `<script src="browser/diffDOM.js">`, and is LGPL-3.0 (861 stars) ([diffDOM](https://github.com/fiduswriter/diffDOM)). LGPL is workable for a script tag but awkward to bundle into a permissively licensed overlay; a 100-line structural walk (tag + attributes + text per node, keyed by the stable selectors the anchoring doc chooses) is enough for "which elements were added, removed, or changed."
- **Screenshot diff in-browser: html-to-image + pixelmatch.** html-to-image (MIT, 7.2k stars) renders a DOM node to `toPng`, `toCanvas`, or `toPixelData` by cloning the node, inlining styles and fonts, and wrapping it in SVG `<foreignObject>`; it "will fail on huge DOM due to the dataURI limit" and cannot render cross-origin canvas content ([html-to-image](https://github.com/bubkoo/html-to-image)). pixelmatch (ISC, zero dependencies, "just a few hundred lines") "works in both Node.js and browser environments," takes `(img1, img2, output, width, height, {threshold: 0.1, includeAA, alpha, diffColor})`, and returns the mismatched-pixel count using an OKLab-based perceptual metric ([pixelmatch](https://github.com/mapbox/pixelmatch)). Resemble.js (MIT) is the canvas-native alternative with `misMatchPercentage`, `diffBounds`, and `ignoreAntialiasing`/`ignoreColors` ([Resemble.js](https://github.com/rsmbl/Resemble.js)). Both libraries are on cdnjs/jsDelivr, so they load inside a Claude Code artifact. The DiffSpot result in [eval-tuning-loops/01 §2](../eval-tuning-loops/01-grading-generated-prototypes.md) — VLMs miss fine CSS changes — is the reason to compute the pixel diff and *show* it rather than ask a model what changed.
- **Re-anchoring comments across versions: use a selector chain and flag orphans.** The W3C Web Annotation model (Recommendation, 2017) defines `CssSelector`, `XPathSelector`, `TextQuoteSelector` (`exact` plus `prefix`/`suffix`), `TextPositionSelector`, and `FragmentSelector`, and lets a selector be "refinedBy 1 or more other Selectors … considered to be alternatives that will result in the same selection" ([Web Annotation](https://www.w3.org/TR/annotation-model/)). Store each comment's anchor as that chain; on a new version key, try each selector in order; a comment whose chain resolves is carried forward with a `re-anchored` flag; one that resolves to nothing becomes an **orphan** filed under the old version key (Figma Make's "Other versions" bucket). Never silently drop or silently re-attach.
- **"What changed since your last comment."** GitHub's PR view offers a "changes since last review" diff that is "the equivalent of a git diff between the PR's head commit when you reviewed it and its new head commit now," and it breaks on rebases ([Daisy Brenecki](https://daisy.wtf/writing/github-changes-since-last-review/); GitHub's docs page describes marking files "viewed," which are "unmarked as viewed" when the file changes ([GitHub](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/reviewing-proposed-changes-in-a-pull-request))). The overlay equivalent: each reviewer's last-seen version key is stored per prototype; opening a newer key shows the DOM-diff summary from that key, the pixel-diff heat map, and the list of their comments split into carried / orphaned. Because keys are content hashes, the "rebase" failure cannot happen — any prior version's bytes are recoverable from the sidecar.

### Open questions
- html-to-image rasterizes from the DOM, not from the compositor; will its output differ enough from a real screenshot to make pixel diffs noisy on shadows and fonts? Needs a bake-off against Playwright screenshots on the same page.
- Should orphaned comments be auto-summarized ("3 comments on elements that no longer exist") and offered as a prompt back to the generator? §7 says yes.

## 7. Cross-session continuity for vibe coding

### What it is
How review state from session N — comments, grades, orphans, the reviewer's verdicts — reaches session N+1 so it shapes the next generation: a sidecar file read at `SessionStart`, a skill that digests open comments, memory files, and the repo's ledger and skill change record as the destinations.

### Why it matters
"Each Claude Code session begins with a fresh context window" ([memory](https://code.claude.com/docs/en/memory)). Everything the overlay collected is invisible to the next generator unless something injects it. If comments do not reach the session, the loop in [eval-tuning-loops/05](../eval-tuning-loops/05-loop-architecture-and-governance.md) has no feedback edge.

### Key findings
- **A `SessionStart` hook is the injection point, and 10,000 characters is the budget.** `hookSpecificOutput.additionalContext` is "added to Claude's context at the start of the conversation, before the first prompt"; strings over 10,000 characters are written to a file with a path and preview substituted ([hooks](https://code.claude.com/docs/en/hooks)). So the hook must *summarize*: open comment count per prototype, the last grade, the orphaned-comment list, and a pointer to the sidecar — not the comment bodies. On `source: "resume"` the hook should say "since you last ran, N new comments" (the hook input includes `seconds_since_last_response`).
- **A skill, not memory, holds the procedure.** Auto memory is "machine-local," loads only "the first 200 lines or 25KB" of `MEMORY.md`, and records `user`/`feedback`/`project`/`reference` notes, skipping "anything it can derive from the codebase" ([memory](https://code.claude.com/docs/en/memory)) — the wrong place for a review ledger that must be shared. CLAUDE.md is for "facts Claude should hold in every session"; the docs say to move multi-step procedures to a skill. The right split: CLAUDE.md gets one line ("review state lives in `docs/prototypes/review/`; run `/review-digest` before regenerating a reviewed prototype"), a `/review-digest` skill reads the sidecars and produces the change list, and auto memory is allowed to note preferences ("reviewer r_42 always wants empty states first").
- **The sidecar is the contract.** One directory per prototype ID (§10) holding the stamped HTML per version key, the comment file, the grade records, and `review.md` — a human-readable digest the skill regenerates. It is committed, so it survives machines and teammates; the Claude Code artifact URL and the Vercel branch are recorded in it, not the other way round. This is the "repo-native" answer that [design-sdlc/03](../design-sdlc/03-prototype-governance-outside-the-codebase.md) reached for the ledger; the overlay writes to it via a copy-as-JSON export in a single-file artifact (an artifact "can't store data submitted through a form" — the docs' own "Copy as prompt" pattern is the workaround) and directly via a dev-server endpoint in Vite/Next.
- **Destinations already exist; add columns, do not add tables.** The ledger row in [skill-resources/prototype-governance.md](../../../skill-resources/prototype-governance.md) (id, question, tool, link, DS version, owner, status, expiry) gains `current_version` (content hash) and `review_sidecar` (path). The skill change record in [eval-tuning-loops/05](../eval-tuning-loops/05-loop-architecture-and-governance.md) gains the list of grade IDs and version keys that motivated the change, so "rule edit X was caused by comments on versions A, B" is a query. The grade record's `artifact` block gains `content_sha256` next to `commit`.
- **Resume and fork semantics affect provenance.** `claude --resume <id>` restores "the full history, including tool calls and results" and the model; `--fork-session`/`/branch` give "their own session IDs"; `/clear` saves the previous conversation and `SessionEnd` fires with `reason: "clear"` ([sessions](https://code.claude.com/docs/en/sessions); [hooks](https://code.claude.com/docs/en/hooks)). A page regenerated after a fork carries a *new* `session_id`; the stamp's `wasRevisionOf` (previous content hash) is what preserves lineage, because no hook field carries the parent session.
- **Peers.** Cursor's `conversation_id` persists across turns and its `sessionStart` hook exists ([Cursor](https://cursor.com/docs/hooks)); Copilot's `sessionStart` has `source: "resume"` ([Copilot](https://docs.github.com/en/copilot/reference/hooks-reference)); Codex has `SessionStart` ([Codex](https://learn.chatgpt.com/docs/hooks)). The same sidecar-plus-start-hook pattern ports to all three; only the hook JSON differs.

### Open questions
- Should `SessionStart` inject the digest unconditionally, or only when the working directory contains a reviewed prototype (a `paths`-scoped rule cannot fire at session start)? A cheap `ls docs/prototypes/review/*/open.json` in the hook decides.
- When a comment thread is "sent to Claude" on an artifact, the publishing session answers live; how does that reply get into the sidecar so session N+1 sees it? The artifact tool's `comments` action can be run by the digest skill — not tested here.

## 8. Cross-cutting themes

1. **The stamp is the API.** No host, vendor, or framework stamps generation provenance; every one of them stamps *something* (`data-dpl-id`, `author`, "Built with v0"). The overlay's one non-negotiable is a JSON block with a schema version, written at generation time, ignored-unknown-keys.
2. **Hash the bytes, mask the stamp.** A content-addressed key is the only version identity that is stable across machines, honest about change, and computable in a `file://` page. Masking the stamp and the overlay script out of the hash is what makes it usable.
3. **Automatic is session + turn + tool call; declared is skill + rules + catalog.** Claude Code, Cursor, Codex, and Copilot all hand hooks a session ID and a working directory; three of four hand over a turn ID; none hands over a skill version. The generation skill has to write its own identity, mechanically.
4. **Borrow names and shapes, not machinery.** PROV relation names, the in-toto Statement envelope, SLSA's parameter/dependency split, OTel GenAI attribute names, and the kernel's `Assisted-by:` trailer cost nothing to adopt. Signing, RDF, C2PA manifests, and AI-BOMs are for a later, different problem.
5. **Old comments are evidence, not clutter.** Figma Make's "Other versions" bucket and Web Annotation's selector chains agree: carry what re-anchors, keep what does not as orphans against the old key, and never drop silently.
6. **The next session reads a digest, not a database.** 10,000 characters of `additionalContext` and a committed sidecar are enough; the ledger and the skill change record are where the loop closes.

## 9. Recommendations

- **Stamp every generated page with the §10 JSON block and `data-proto-version`**, written by a `PostToolUse` hook on `Write|Edit` (Claude Code), a `transformIndexHtml` plugin (Vite), or `NEXT_PUBLIC_PROTO_*` constants plus `deploymentId` (Next). Add `<meta name="generator" content="proto-builder/1.4.2 via claude-code/2.1.x">` as the human marker (§1).
- **Make `content_sha256` of the stamp-masked bytes the comment and grade key; record `git_blob` beside it** as the repo join. The overlay hashes in-browser only for unstamped pages and prefixes the key `unstamped:` (§3).
- **Capture automatically what the tooling offers — `session_id`, `prompt_id`, `tool_use_id`, `agent_id`, `cwd`, Claude Code version, model when present — and make the skill declare the rest mechanically** into `.proto/generator.json`: `metadata.version` from its own SKILL.md, `git hash-object` of rules, the exemplar-set and catalog version it was given (§2, §4).
- **Name fields with OTel GenAI attributes and PROV relations** so API-pipeline traces (Langfuse `sessionId`/`release`, LangSmith `thread_id`) and Claude Code OTel events join on the same keys; set declared identifiers in `OTEL_RESOURCE_ATTRIBUTES` when telemetry is on (§4, §5).
- **Wrap the stamp in an in-toto Statement shape** (`subject[].digest.sha256`, `predicateType: "https://<your-org>/proto-provenance/0.1"`) so a signed attestation at promotion time is a wrapper, not a rewrite (§5).
- **Adopt `Assisted-by: Claude:<model-id>` and `Prototype: PROTO-YYYY-NNN` commit trailers** alongside the existing `Co-Authored-By`; extend the ledger-link gate to require the trailer (§5).
- **Ship version comparison as side-by-side iframes first, pixel diff (html-to-image + pixelmatch) second, structural DOM diff third; re-anchor comments through a selector chain and file orphans under the old key** (§6).
- **Commit a per-prototype sidecar directory; inject a ≤10k-character digest at `SessionStart`; put the procedure in a `/review-digest` skill; add `current_version` and `review_sidecar` to the ledger row and grade IDs to the skill change record** (§7).

| Provenance field | Captured automatically by | Declared by | Used by which loop step |
|---|---|---|---|

<script type="application/json" id="proto-provenance">
{
  "_type": "https://in-toto.io/Statement/v1",
  "subject": [{ "name": "invite-sheet.html", "digest": { "sha256": "9f2c…e1a0" } }],

`.claude/hooks/proto-session-start.sh` — records the session and injects the review digest (≤10k chars):

```bash
#!/usr/bin/env bash
set -euo pipefail
input=$(cat)
sid=$(jq -r .session_id <<<"$input"); src=$(jq -r .source <<<"$input")
model=$(jq -r '.model // empty' <<<"$input")
mkdir -p .proto
jq -n --arg sid "$sid" --arg model "$model" --arg src "$src" --arg cwd "$(pwd)" \
  '{session_id:$sid, model:($model|select(.!="")), source:$src, cwd:$cwd, started_at:(now|todate)}' > .proto/session.json
digest=""
for open in docs/prototypes/review/*/open.json; do
  [ -f "$open" ] || continue
  id=$(basename "$(dirname "$open")")
  n=$(jq 'length' "$open"); orphans=$(jq '[.[]|select(.orphaned)]|length' "$open")
  ver=$(jq -r '.current_version' "docs/prototypes/review/$id/review.json")
  digest+="- $id @ $ver: $n open comments ($orphans orphaned). Run /review-digest $id before regenerating."$'\n'
done
digest=${digest:0:9000}
jq -n --arg ctx "$digest" '{hookSpecificOutput:{hookEventName:"SessionStart",additionalContext:("Prototype review state:\n"+$ctx)}}'
```

`.claude/hooks/proto-stamp.sh` — stamps any `.html` the model just wrote; declared fields come from `.proto/generator.json`, which the generation skill writes (its SKILL.md body: `echo '{"gen_ai.agent.name":"proto-builder","gen_ai.agent.version":"1.4.2","rules_sha":"'$(git hash-object .claude/rules/*.md CLAUDE.md | sha256sum | cut -c1-16)'", …}' > .proto/generator.json`, using `${CLAUDE_SESSION_ID}` if it wants to cross-check):

```bash
#!/usr/bin/env bash
set -euo pipefail
input=$(cat)
file=$(jq -r '.tool_input.file_path // empty' <<<"$input")
[[ "$file" == *.html ]] || exit 0
[ -f "$file" ] || exit 0
sid=$(jq -r .session_id <<<"$input"); pid=$(jq -r '.prompt_id // empty' <<<"$input")
tuid=$(jq -r '.tool_use_id // empty' <<<"$input"); aid=$(jq -r '.agent_id // empty' <<<"$input")
model=$(jq -r '.model // empty' .proto/session.json 2>/dev/null || true)
prev=$(grep -o 'data-proto-version="[^"]*"' "$file" | head -1 | cut -d'"' -f2 || true)
# mask stamp + overlay, hash the rest
masked=$(perl -0pe 's#<script type="application/json" id="proto-provenance">.*?</script>##s; s#data-proto-version="[^"]*"#data-proto-version=""#; s#<script[^>]*data-proto-overlay[^>]*>.*?</script>##s' "$file")
sha=$(printf '%s' "$masked" | shasum -a 256 | cut -d' ' -f1)
blob=$(git hash-object "$file" 2>/dev/null || echo null)
commit=$(git rev-parse HEAD 2>/dev/null || echo null)
gen=$(cat .proto/generator.json 2>/dev/null || echo '{}')
stamp=$(jq -n --arg sha "$sha" --arg name "$(basename "$file")" --arg sid "$sid" --arg pid "$pid" \
  --arg tuid "$tuid" --arg aid "$aid" --arg model "$model" --arg blob "$blob" --arg commit "$commit" \
  --arg prev "$prev" --argjson gen "$gen" --arg ver "$(claude --version 2>/dev/null | head -1)" '
  {_type:"https://in-toto.io/Statement/v1",
   subject:[{name:$name,digest:{sha256:$sha}}],
   predicateType:"https://example.org/proto-provenance/0.1",
   predicate:{schema:"proto-provenance/0.1", proto_id:($gen.proto_id//null), generated_at:(now|todate),
     git:{blob:$blob,commit:$commit},
     wasGeneratedBy:{tool:"claude-code","tool.version":$ver,"gen_ai.conversation.id":$sid,"prompt.id":$pid,
       "gen_ai.tool.call.id":$tuid,"agent.id":($aid|select(.!="")),"gen_ai.response.model":($model|select(.!=""))},
     used:$gen, wasRevisionOf:($prev|select(.!="")),
     review:{sidecar:("docs/prototypes/review/"+($gen.proto_id//"unfiled")+"/")}}}')
# inject or replace
if grep -q 'id="proto-provenance"' "$file"; then
  perl -0pi -e 's#<script type="application/json" id="proto-provenance">.*?</script>#<script type="application/json" id="proto-provenance">'"$(printf '%s' "$stamp" | sed 's/[&\\#]/\\&/g')"'</script>#s' "$file"
else
  perl -0pi -e 's#(<head[^>]*>)#$1\n<script type="application/json" id="proto-provenance">'"$(printf '%s' "$stamp" | sed 's/[&\\#]/\\&/g')"'</script>#' "$file"
fi
perl -0pi -e 's#<html([^>]*?)( data-proto-version="[^"]*")?#<html$1 data-proto-version="sha256:'"$sha"'"#' "$file"
jq -n --arg m "Stamped $(basename "$file") as sha256:${sha:0:12} (session ${sid:0:8}, prompt ${pid:0:8})" '{systemMessage:$m}'
```

Notes: the hook rewrites the file after Claude's `Write`, so `/rewind` will not restore the stamp (bash-modified files are not checkpointed); builder output written by a shell command needs the same script under a `FileChanged` hook; hook stdout is capped at 10,000 characters, which the `systemMessage` respects. For Vite, the same masking and JSON go in a `transformIndexHtml` plugin reading `process.env`/`git`; for Next, emit the block from the root layout using `NEXT_PUBLIC_PROTO_*` constants and let `deploymentId` add `data-dpl-id`.

### (c) Sidecar-file layout

```text
docs/prototypes/
├── ledger.md                              # one row per PROTO- id; gains current_version + review_sidecar columns
└── review/
    └── PROTO-2026-041/
        ├── review.json                    # {proto_id, current_version, versions:[{sha256, generated_at, session_id, prompt_id, file}], reviewers:{r_42:{last_seen:"sha256:…"}}}
        ├── review.md                      # human digest regenerated by /review-digest: open, orphaned, resolved, last grade
        ├── open.json                      # comments not yet resolved; each: {id, version:"sha256:…", anchor:{selectors:[CssSelector, TextQuoteSelector…]}, body, label, severity, author, created_at, orphaned:false, re_anchored_from:null}
        ├── resolved.json                  # closed threads, with the version they were closed on
        ├── grades/
        │   ├── g_01J9….json               # grade record (eval-tuning-loops/01) with artifact.content_sha256 set
        │   └── …
        ├── versions/
        │   ├── sha256-9f2c…e1a0.html      # stamped bytes of each reviewed version (enables "changes since" without git archaeology)
        │   └── sha256-4b71…c902.html
        └── shots/
            └── sha256-9f2c…e1a0@1280.png  # overlay-captured evidence; stamped with digitalSourceType=trainedAlgorithmicMedia in the grade
```

The overlay in a single-file artifact exports `open.json` entries via a copy-to-clipboard control (artifacts have no backend); in Vite/Next dev it POSTs to a dev-only `/__proto/review` route that appends to the same files. The `/review-digest <id>` skill reads this directory, rewrites `review.md`, and returns the orphan list and last grade as the change brief for the next generation.
