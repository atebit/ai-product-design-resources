# Q4 — Structural compression via progressive disclosure

Corpus measured directly from `skills/*/SKILL.md` and `skills/*/references/**` at the pinned commit.
Aggregate figures I measured: 14 `SKILL.md` files = **211,115 bytes**; 14 frontmatter `description:` lines = **6,437 bytes**; reference material = **862,620 bytes of Markdown + 452,967 bytes of `plugin-api-standalone.d.ts`** (1,315,587 bytes total). These are close to, but not identical to, the prompt's cited 209,893 / 7,146 / ~888KB — the gap is almost certainly `wc -c` counting trailing newlines and my totals including the `.d.ts` separately from the Markdown references. All numbers below are labeled **[measured]** (counted directly) or **[inferred]** (my estimate of what would move and what it would cost).

## 2. What must stay resident, and where the rule breaks

**Hypothesis under test:** content needed to decide *whether* and *when* to act must be resident in SKILL.md; content needed only to *execute* a step correctly can be fetched on demand.

This holds cleanly in the smallest skills: `figma-create-new-file` (3,946B, no references dir) is nearly all decision logic — resolve a `planKey`, call one tool, interpret the result — there is no "how" to defer because the tool call *is* the whole task. Same for `figma-design-to-code` and `figma-generative-plugins`.

It also explains the corpus's best-compressed skill, `figma-use-figjam` (6,943B): every paragraph is a gate ("use `get_figjam` upfront," "get_metadata does NOT work on FigJam files," "createPage() throws in FigJam") and every "how" (13 node-type references, 6,943B → 156KB fanned out) is one link away.

Where it breaks:

- **`figma-implement-motion`'s merge algorithm (Steps 1–3, ~2,500 words) is execution detail by the letter of the rule, but it is also the entire value of the skill** — it is not optional "how," it is the one thing a generic LLM cannot infer from first principles (which of two id fields wins, when `fallbackNodeId` is safe, how absolute vs. offset rotation values compose). Rule-of-thumb category ("decide" vs. "execute") doesn't cleanly separate "core inventive logic unique to this tool's contract" from "generic scripting detail." The corpus's own resolution is pragmatic, not rule-following: the merge algorithm stays resident because getting it wrong produces silently-incorrect motion (a correctness gate in disguise), while the truly generic edge case — interleaved-transform nesting order — is *still* resident today (lines 90–98) even though it only fires when a rare structural pattern is detected, i.e. it is a "how" that the rule says should be fetchable. That is a real gap between the rule and the current implementation, and Table 1 flags it as the highest-value line item to move.
- **`figma-generate-design` inverts the pattern:** two-thirds of its bulk (Steps 2a–2c, ~9,000B of the 33,487B) is inline runnable scripts — pure "how" — while the actual decision gates ("Forbidden: search_design_system until 2a-i is attempted or logged N/A") are compact and already load-bearing. This skill demonstrates the rule holds in the sense that violating it (leaving "how" resident) is exactly what produced its outlier size; it does not demonstrate the rule breaking.
- **Checklists are a structural blind spot the rule doesn't address.** `figma-use`'s §8 Pre-Flight Checklist (24 items) mostly restates §1's 18 numbered rules in imperative-checkbox form. Both are "resident" by the rule (they're decision/verification gates), but the restatement itself is redundant bulk the rule has no opinion on — deduplicating rule-statement vs. checklist-restatement is a wording problem for the companion researcher, not a disclosure problem, but it inflates the "must stay resident" baseline this analysis has to accept.

## 3. Existing routing tables — are they good?

`figma-use` §10 "Reference Docs" (10 rows, format: file / when to load / what it covers) is the most complete table in the corpus and is explicitly named in the prompt as the reference case for `plugin-api-standalone.d.ts`. It gives three signals per row — **file**, **trigger condition**, **content summary** — which is enough for an agent to decide to fetch without opening the file. The `.d.ts` row explicitly says "grep for relevant sections as needed," which is the one instruction elsewhere in the corpus proven to prevent a 453KB dead load.

`figma-use-figjam`'s table (13 rows) is arguably *better* signal per byte: each row starts with an imperative ("Read this for…") rather than a passive "when to load," and — critically — the skill adds a meta-instruction above the table ("Loading Reference Docs Efficiently": batch multiple reference reads into one parallel tool-call message) that the `figma-use` table lacks. That meta-instruction is itself a compression technique: it doesn't shrink any single reference, but it collapses N sequential round trips into 1, which matters more than byte count under the rate-limit constraint in §4.

Two improvements that would generalize across all 14 tables:
1. **Name the trigger phrase, not just the topic.** `figma-use`'s row "component-patterns.md — Creating components/variants" tells the agent *what's in the file* but not *what the user said* that should cause the fetch. `figma-generate-design`'s inline style ("If it does and this is a web app, you **must** run…") is more actionable because it's phrased as a condition-action pair. Tables should adopt that phrasing: "Load when the task involves creating a COMPONENT_SET or combining variants" rather than "Creating components/variants."
2. **Annotate approximate reference size in the table.** None of the 14 tables tell the agent how expensive a fetch is. A one-word size tag (`small`/`large`) next to `gotchas.md` (53,421B, the largest non-`.d.ts` reference in the corpus) versus `effect-style-patterns.md` (3,215B) would let the agent budget multiple fetches in one batch, similar to how the `.d.ts` row already flags itself as too large to load whole.

## 4. The over-disclosure failure mode

Two costs compound when content over-fragments into references: (a) each reference read is a separate tool round trip, and (b) for MCP-resource-served skills, `get_figma_skill` / `read_skill_uri` are **not** on Figma's rate-limit exemption list (only `add_code_connect_map`, `create_new_file`, `whoami` are exempt per the prompt's stated list) — so every unnecessary fetch spends quota that a resident sentence would not.

This corpus already shows where the balance tips the wrong way: `figma-use-slides/references/slide-lifecycle.md` (2,208B) and `slide-grid.md` (3,058B) are two of the smallest files in the whole reference tree — each is a separate fetch for content that would cost less as a combined ~5,000B file, and less still folded back as two subsections of a single "Slide Structure" reference. Splitting content this small into its own file trades a fixed round-trip/quota cost for a marginal reduction in resident bytes that is smaller than the routing sentence needed to describe it. The same risk appears, to a lesser degree, in `figma-use/references/effect-style-patterns.md` (3,215B) and `validation-and-recovery.md` (3,873B) sitting alongside `gotchas.md` at 53,421B in the same directory — the size variance across one skill's own reference set is a 15–20x spread, suggesting no consistent file-size floor is currently applied.

**[Inferred] balance point:** given the round-trip/quota cost is fixed per fetch regardless of file size, a reference file below roughly 4–5KB is rarely worth a dedicated fetch unless it is fetched in true isolation from everything else in its directory (e.g., a single narrow gotcha nobody else needs). Above that floor, moving content out is close to strictly positive as long as a routing sentence exists, because the fetch cost is amortized over more bytes not paid resident on every trigger. The counter-force is fan-out breadth: `figma-use-figjam` mitigates its 13-file split by explicitly instructing batched parallel reads (§3), which is the correct fix for fragmentation — batch the fetch, don't avoid the split.

## 5. Ranking by restructuring headroom

Ranked by **[inferred]** bytes plausibly movable with a viable routing sentence, weighted by how often the skill is loaded (figma-use's absolute savings compound because it is a mandatory prerequisite for every `use_figma` call, per its own frontmatter description):

1. **figma-generate-design** (33,487B SKILL.md, only 6,463B of references — the most lopsided ratio in the corpus, confirmed by header/line inspection: lines 67–226 are three full discovery scripts and lines 261–372 are full build/icon-import scripts). Highest raw headroom, ~7–8.5KB.
2. **figma-use** (34,645B, largest SKILL.md by absolute size, but 688KB of references already — headroom is smaller in percentage terms, ~2.5–3KB, but it's the highest-traffic file in the corpus so the byte savings recur on every invocation).
3. **figma-implement-motion** (23,279B). **Verified**: fenced-code share is 0.6% of file bytes (134 of 23,279 measured via extracting text between ``` fences) — this matches the prompt's "~1% fenced code" claim closely. My own normative-density measure (lines containing must/never/always/should/don't) came out at 9.6% (14/146 lines), not the prompt's "~3%" — the discrepancy is methodological (line-level keyword match vs. sentence-level classification), but both measures agree the file is dense, un-coded decision prose rather than runnable snippets. It genuinely reads as prose-heavy, but per §2 much of that prose is irreducible merge-algorithm logic; the movable slice is the ~4KB interleaved-transforms edge case.
4. **figma-use-slides** (22,033B). **Verified**: 5.3% fenced-code share (1,163B of 22,033B) and 13.6% normative-line density (29/214) — denser in imperative language than figma-implement-motion, consistent with it being workflow/etiquette guidance (design thinking, section naming, speaker-note tone) rather than an API contract. ~2.2KB of that (speaker-note style prose) is cleanly fetchable.
5. **figma-code-connect** (26,669B, 19.6% code share, already reasonably reference-backed at 33KB) — moderate headroom (~2KB) in its inline quick-reference section.
6. **figma-generate-library** (23,435B) — low headroom; already the most disciplined large skill (169KB across 7 focused references, each named by phase).
7. **figma-generate-diagram** (10,272B) — small absolute headroom (~1KB); already routes per-diagram-type detail to 7 references.
8–14. **figma-use-figjam, figma-use-motion, figma-shaders, figma-swiftui, figma-design-to-code, figma-generative-plugins, figma-create-new-file** — negligible headroom; each is already either fully reference-routed (figjam, motion, shaders, swiftui) or too small to decompose further without the routing sentence costing more than the content it would move (the four smallest skills, all under 7KB).

**Bottom line:** the lever pays most where a skill's SKILL.md-to-references ratio is inverted relative to the corpus norm (figma-generate-design is the outlier at ~5:1 SKILL.md-to-reference bytes, versus figma-use's ~1:20 and figma-generate-library's ~1:7), and pays least where a skill is already small enough that no reference split survives the fixed per-fetch cost from §4.
