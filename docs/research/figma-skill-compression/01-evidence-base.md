# Q1: What does published evidence actually establish about safely removing content from agent skill files?

## Provenance and status of the primary source

**SkillReducer: Optimizing LLM Agent Skills for Token Efficiency.** Yudong Gao, Zongjie Li, Yuanyuan Yuan, Zimo Ji, Pingchuan Ma, Shuai Wang. HKUST / Tsinghua / Zhejiang University of Technology. arXiv:2603.29919v2 [cs.SE], submitted 2026-03-31, revised 2026-06-24.

This is an **unreviewed arXiv preprint**, not a published/peer-reviewed paper. No venue is listed; the "open-source tool" is promised only "upon acceptance" (i.e., not yet accepted anywhere). Read the full PDF (13 pages + appendices), not just the abstract page.

A second load-bearing fact for skepticism: the external benchmark the paper leans on for its "0.965 retention / 100% pass" headline, **SkillsBench**, is *also* a bare arXiv preprint from a different group (Li et al., arXiv:2602.12670, 2026) submitted about a month before SkillReducer. It is not an established or independently validated benchmark — it's a contemporaneous, equally-unvetted artifact. Treat "SkillsBench" as "a benchmark one other 2026 preprint proposed," not as ground truth.

## 1. The taxonomy (the single most transferable artifact)

Section III-B defines a **five-category taxonomy** for skill-body content, built from a stratified sample of 90 skills (30 each from three sources: Wild/GitHub, SkillHub marketplace, developer-Community), yielding n=15,107 paragraph-level items:

| Category | Definition | Share of items |
|---|---|---|
| **Core rule** | Actionable instructions the agent must follow | 38.5% |
| **Background** | Explanations, rationale | 40.7% |
| **Example** | Illustrative code snippets / I-O pairs | 12.9% |
| **Template** | Boilerplate for copy-paste | 7.6% |
| **Redundant** | Repeated content | 0.3% |

"Over 60% non-actionable" = Background + Example + Template + Redundant (61.5%). **Only Core Rule is measured as unconditionally actionable.**

**Classification method:** an LLM classifier (DeepSeek-V3, temperature 0) with structured output, plus a cross-validation pass where each item's label is re-evaluated in light of its neighbors' labels (up to 2 rounds). If classification fails validation after 3 retries, the item defaults to `core_rule` — a conservative fallback, which matters: the pipeline is designed to err toward keeping content, not cutting it.

**Independent validation of the taxonomy:** the authors embed all 15,107 items and run GMM clustering (k=5, chosen at the first local peak of silhouette score). Five clusters emerge that roughly align with the LLM-assigned labels — but the authors explicitly flag the **silhouette score is only 0.393**, i.e., "moderate separation," not clean separation. This is an honest caveat: the taxonomy is a useful organizing heuristic, not a sharply-defined partition of skill content. Category boundaries (e.g., an example that also encodes a rule) are fuzzy by the authors' own measurement.

## 2. Stage 1 (routing/description) and Stage 2 (body) methods

**Stage 1 — adversarial delta debugging on descriptions.** An LLM segments the description into "semantic clauses" (coarser than sentences, finer than words). A simulated routing oracle O(d, Q, C) tests whether a candidate description d still causes the agent to pick the target skill over 4 TF-IDF-similar distractors plus one **adversarially LLM-generated "shadow" skill** (topically similar, functionally distinct — e.g., "JWT authentication" → generated distractor "OAuth 2.0 token refresh"). DDMIN (classic delta-debugging, O(n log n) oracle calls) finds a 1-minimal clause subset that still passes the oracle; retained clauses are individually paraphrased shorter if the oracle still passes. Then **Phase 2 does real-environment validation**: the compressed description is actually deployed and tested against the real Claude Code CLI trigger behavior, with up to 3 rounds of "selective restore" (adding back the single most-helpful deleted clause) if the fast simulated oracle turns out to have been too aggressive, falling back to the original description if restoration fails. This two-phase design is a genuine strength: **40.8% of skills needed at least one restore round**, meaning the fast/cheap oracle alone is measurably too optimistic about what can be cut — real-environment checking caught over a third of over-compressed cases.

**Stage 2 — taxonomy-driven classification + progressive disclosure.** Each body paragraph gets a taxonomy label (above). Only `core_rule` items stay in the always-loaded core; background/example/template items are split into on-demand reference files (`examples.md`, `templates.md`, `background.md`) each annotated with a "when" trigger clause and 3-5 topic keywords so the agent can decide to `read_file` them without reading them first; `redundant` items are discarded. Reference files are separately deduplicated against the body. Two quality gates follow:
- **Gate 1 (faithfulness):** an LLM checks, per content-type, whether all "operational concepts" from the original survive somewhere in {core, references}; failing types are rolled back wholesale to their uncompressed original — not patched, replaced entirely.
- **Gate 2 (task-based eval) + feedback loop:** 5 generated tasks per skill (mixing core-only and needs-reference tasks) are run under the compressed skill; if any task scores worse than under the original, the specific missing content is identified and "promoted" back into the always-loaded core **verbatim, uncompressed**, and the loop repeats (capped at 2 iterations).

**Type-specific compression is not uniform**: core rules are merged/tightened into bullets; examples are deduplicated to "one best example per concept" (60-70% count reduction); background is summarized "while preserving all unique factual claims such as numbers, thresholds, and API endpoints" — an explicit, important carve-out (see §5).

## 3. The quality story — where +2.8% hides real regressions

This is where the "compression is free" framing needs the most pushback.

- **Headline number:** Condition C (compressed) scores 0.742 mean vs. Condition A (original) 0.722 mean across all 600 skills — the origin of "+2.8%" (0.742/0.722 − 1 ≈ 2.8%). p=0.002, but **Cohen's d = 0.107**, i.e., a small effect size. This is an *average*, and 14.0% of skills scored *worse* under compression (vs. 25.3% that improved) — so yes, the average genuinely does hide a substantial regression tail.
- **Ceiling inflation:** 19.8% of the 600 skills are "ceiling" cases where D=A=C=1.0 (no-skill, original, and compressed all score perfectly — the tasks were too easy to discriminate anything). Excluding these (N=481, "non-ceiling"), the pass rate drops from 86.0% to **82.5%**, and the effect only reaches p=0.010 (weaker than the headline p=0.002).
- **Decomposing the 14.0% regressions (84 skills):** the authors themselves break this down — roughly **50% are attributable to "skill obsolescence"** (the agent does equally well with *no skill at all*, so the "regression" isn't really about compression quality), **17% to evaluation noise**, and only **33% to "true compression regression."** That final category is ~4.7% of the full 600-skill set. So the paper's own honest accounting is: about 1 in 20 skills suffers a genuine, compression-caused quality loss — not zero, but importantly not the 14% headline regression figure either, in either direction (it's simultaneously smaller than 14% for "real" harm, but the underlying 14% number itself is real and not explained away).
- **The named failure mode — "example-as-specification":** the recurring pattern behind true regressions is that **examples were implicitly serving as the specification** for expected behavior; when the classifier (correctly, by taxonomy) moved them to on-demand reference modules, the agent lost behavior it needed and didn't always retrieve the reference in time. The authors call this "a fundamental limitation of taxonomy-based classification: when authors intentionally embed rules within examples, automated separation can lose implicit dependencies" (Appendix D). This is the load-bearing caveat for any API-shaped skill where "example calls" *are* the parameter-shape documentation.
- **Is there a "cliff"?** The authors ran a sensitivity analysis by compression ratio bucket (Table VII): retention stays in a narrow band, **0.910–0.956**, from <20% compression up to >80% compression, with pass rates consistently >80% in every bucket. Their claim is explicitly that there is *no* cliff — aggressive compression is not riskier than light compression **in this evaluation**. But this needs a major caveat (next point).
- **Self-referential evaluation (authors' own admitted threat to validity):** Gate 2 — the task-based quality metric — is used *both* as the optimization feedback signal (to decide what to promote back to core) *and* as the reported evaluation criterion. The paper states this plainly: "Gate 2 serves dual roles (feedback signal and evaluation criterion), so the 86.0% pass rate reflects optimization-to-criterion." In other words, the system was tuned against the very test it's graded on. The independent SkillsBench check (below) is offered as a partial mitigation, but SkillsBench turns out to have its own severe ceiling problem.
- **Baseline comparison undercuts "compression is free" too:** in the head-to-head at matched token budgets (N=50, Table IV), SkillReducer's raw score (0.909) is still *below* the uncompressed original (0.921) — it just beats LLMLingua (0.767), direct LLM compression (0.866), truncation (0.791), and random sentence removal (0.694) by a wide margin. SkillReducer's retention (0.949) is the best of the compression methods tested, but it is not shown to be *lossless* relative to doing nothing — only "least lossy among compression baselines at this budget."

## 4. What "functional quality" is actually measured as, and does it transfer to Figma-canvas tasks?

Gate 2 quality is: 5 LLM-generated tasks per skill, each with a rubric of required criteria extracted from the original body, scored by one of two mechanisms — **52.3%** are code-execution tasks graded by deterministic pytest-style assertions, **47.7%** are graded by an LLM judge (Qwen3.5) against the rubric, cross-validated against the deterministic subset (Cohen's κ=0.939 on 1,646 overlapping tasks). This is a reasonably rigorous design *for the domain it was built on* — but that domain is dominated by **text/knowledge-generation skills**: PDF processing, spreadsheet analysis, marketing strategy, git-commit-message generation, BigQuery schema navigation, document editing. Success in these tasks is largely about *producing correct textual/structured output* judged against a rubric or a script assertion on that output.

Figma-canvas skills are a different shape of task: **write-heavy, stateful, API-schema-precise** (node IDs, coordinate systems, hierarchy, exact parameter shapes for tool calls), where failure is often **silent and structural** (wrong bounding box, broken nesting, a valid-looking but incorrect API call) rather than a wrong paragraph of text a rubric can catch. Three specific reasons to doubt transfer:
1. The paper's own dominant regression mechanism — **example-as-specification** — is exactly the risk profile of an API-shaped skill: code examples in Figma skills likely encode exact call shapes/parameter conventions that a generic "keep only prose rules, defer examples" split would sever.
2. None of the 600 evaluated skills, the SkillsBench 87 tasks, or the cross-framework OpenCode check are design-tool/canvas-manipulation skills; external validity is explicitly scoped by the authors to "the skill protocol proposed by Anthropic," with generalization to other platforms/domains stated as untested.
3. SkillsBench's own discriminative power is in question (next point) — the paper's cleanest, most "external" quality signal turns out to barely measure anything.

**SkillsBench ceiling problem, in the authors' own words:** "we evaluate on SkillsBench (87 tasks, deterministic pytest verifiers): all 87 pass under both A and C with zero regression, though **condition D (no skill content at all) already passes 86/87**, indicating a ceiling effect. Our Gate 2 evaluation (where D scores only 0.684) better captures the value of skill content." This means the headlined "100% pass rate on SkillsBench" is close to meaningless as evidence that compression preserves skill value — on that benchmark, *having no skill at all* already succeeds 98.9% of the time, so the benchmark isn't sensitive enough to detect degradation either. The paper is commendably candid about this, but any summary that cites "100% on SkillsBench" as a compression-safety proof point is repeating a number the authors themselves say is close to uninformative.

The 0.965 mean cross-model retention figure (5 models, 4 families: Qwen3-max, DeepSeek-V3, Qwen2.5-7B, GLM-5, GPT-OSS-120B) is a real and reasonably interesting generalization result — compressions made by one model (DeepSeek-V3) transfer to being executed by weaker/different models without collapsing. But note: GPT-OSS-120B was evaluated via **flat injection, not real progressive disclosure**, because it lacks tool-calling support — so its high retention (0.982) doesn't test the on-demand-reference mechanism at all, only the body-compression mechanism. None of the five models is a Claude model (Claude Code CLI is used only as the Stage-1 real-trigger validator, not as an evaluated agent), so there is no direct evidence in this paper about Claude-specific behavior under compressed skills — relevant since the target application (Figma's official skills) are specifically Claude-facing.

## 5. Explicit "do not cut" content classes and stated limitations

Content classes the authors explicitly protect or flag as unsafe to cut:
- **Numeric/structured facts inside background text** — "Background content is summarized into a concise paragraph while preserving all unique factual claims such as numbers, thresholds, and API endpoints." This is a direct, explicit exception carved out of an otherwise-aggressive compression stage.
- **Examples that function as implicit specification** — identified post hoc as the main failure mode, not protected by design; the authors call this "a fundamental limitation of taxonomy-based classification."
- **Anything flagged by Gate 1 faithfulness** ("operational concepts") — must appear somewhere in {core ∪ references}, or that content type is rolled back to its original, uncompressed form entirely (a coarse, type-level rollback, not surgical).
- **Anything Gate 2 shows is actually load-bearing for task success** — promoted back into the always-loaded core in its **original, uncompressed form** (compression is not reapplied to promoted content).

Stated threats to validity (Section VII, in the authors' own words):
- *Internal validity:* LLM classification randomness (mitigated by temp-0 + fallback + feedback loop); the dual-role Gate 2 optimization-to-criterion problem noted above.
- *External validity:* all 600 evaluated skills use "the skill protocol proposed by Anthropic"; generalization to other platforms (Cursor, Windsurf) is explicitly untested. Cross-model check covers only 5 models/4 families; other families (e.g., Llama) untested.
- **Wild-skill compression is validated far more weakly than the headline suggests.** The 77.5% mean compression figure on 198 wild GitHub skills used **only Gate 1 (structural faithfulness), with no Gate 2 task-based evaluation at all**, "due to cost." And even on that weaker structural check alone, faithfulness verification **passed for only 74.7% (148/198)** of sampled wild skills — meaning roughly 1 in 4 real-world skills, taken off GitHub and compressed with this pipeline, failed even the "did we keep all the concepts" check, let alone a functional-quality check. This is arguably the single most important caveat for anyone about to apply this taxonomy to a new corpus (like Figma's 14 skills): the strongest quality claims (86% pass rate, 0.965 retention) are backed by expensive Gate-2 task evaluation done on a curated 600-skill set; the cheaper, more broadly-scaled compression numbers (77.5% on wild skills) have a meaningfully worse and only partially-verified quality picture.
- **Model/skill obsolescence** is a confound the authors flag but don't fully disentangle: 10.7% of skills didn't trigger even with their *original* description, and condition D (no skill) scores surprisingly well across the board (0.684 mean internally, 98.9% on SkillsBench) — suggesting some fraction of the "skills preserve quality under compression" result is really "these skills weren't adding much value to begin with," which is a different and less flattering finding than "compression is safe."

## 6. Anthropic's own authoring guidance (for calibration against the academic claims)

From platform.claude.com's official best-practices doc (fetched directly, high confidence — this is first-party, current Anthropic documentation, not a preprint):
- **Keep SKILL.md body under 500 lines**; split into separate reference files when approaching that limit. This is a checklist item, stated as a hard practical guideline, not a taxonomy-derived percentage.
- Description field: max 1,024 characters, must be third-person, must include both *what* the skill does and *when* to use it — description quality is explicitly framed as the single most important lever for correct routing among "100+ available Skills."
- **Default assumption: Claude is already very smart** — the core cutting heuristic Anthropic gives is not a content-type taxonomy but a per-paragraph challenge: "Does Claude really need this explanation? Can I assume Claude knows this? Does this paragraph justify its token cost?" This is compatible with, but coarser than, SkillReducer's five-way taxonomy — it collapses to something like "cut background/explanation the model already knows," without a formal example/template/redundant split.
- **Keep reference files exactly one level deep from SKILL.md** — Claude will partially/lazily read doubly-nested references (e.g., with `head -100`), so nested progressive disclosure silently loses content. This is a concrete mechanical risk not covered in the SkillReducer paper at all (their reference modules are one level deep by construction, but they don't discuss or test deeper nesting).
- **Structure reference files >100 lines with a table of contents** so partial reads still reveal full scope.
- Explicit content-quality anti-patterns: no time-sensitive information (use a collapsed "old patterns" section instead of deleting), consistent terminology, avoid presenting the model with too many options, and — importantly — **"build evaluations first"**: write 3+ test scenarios and a baseline *before* writing extensive documentation, which structurally prevents over-documenting problems that don't exist. This evaluation-first workflow is a practical, cheap analogue to SkillReducer's expensive Gate-2 task generation, achievable without an academic pipeline.
- Utility scripts are explicitly favored over inline code for **deterministic, low-freedom operations** ("solve, don't defer") — they cost zero context tokens until executed and are more reliable than agent-generated code. This maps onto a content class SkillReducer doesn't really address (skills with executable scripts were explicitly out of scope for the paper's cost model: "Scripts... do not consume context tokens in the same way and are out of scope for this work").

## 7. Secondary/community sources (lower confidence — flagged accordingly)

- **github.com/mgechev/skills-best-practices**: a community (non-Anthropic) best-practices repo. Broadly consistent with Anthropic's own doc (500-line SKILL.md limit, one-level-deep references, third-person imperative writing) but adds independent, unverified recommendations: remove README/CHANGELOG/install-guide-style docs from skill bodies, keep "just-in-time loading instructions," and match `name` to the parent directory. Treat as a practitioner opinion, not a validated finding — no evaluation methodology is described.
- **newsletter.swirlai.com "agent skills, progressive disclosure"**: a blog/newsletter post, not a primary or peer-reviewed source. It offers a three-tier framing (discovery/activation/execution) that is directionally consistent with Anthropic's documented architecture, but specific numbers it cites (e.g., "~80 token median discovery cost," "17 official skills total ~1,700 tokens," "skill-creator ~8,000 tokens," "accuracy degrading past 10 tools") could not be independently verified from this fetch and should be treated as unverified secondary claims, not established facts, until checked against a primary source.

## Bottom line for the compression-is-free framing

The evidence does **not** support "compression is free." It supports a more qualified claim: *a taxonomy-driven, gated, feedback-corrected compression pipeline, evaluated mostly on text/knowledge-generation skills using a partially self-referential quality metric, achieves large token savings with a small positive average quality delta and a real, non-trivial regression tail (~14% of skills, of which roughly a third — ~4.7% of the total — are attributable to compression itself rather than noise or skill obsolescence).* The clearest, most defensible transferable finding is the **taxonomy itself** (core rule / background / example / template / redundant) and the general principle that **naive, non-taxonomy-aware compression is measurably worse** (the ablation's "compress-all-without-classify" condition loses 6.8 percentage points of retention versus the full pipeline). The clearest warning sign for Figma's canvas-facing skills specifically is the paper's own named failure mode, "example-as-specification" — precisely the pattern likely to recur in API-shaped, write-heavy design-tool skills where example calls encode structure that prose rules don't fully restate.
